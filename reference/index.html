    API reference¶

    Everything below is exported from django_spec_html directly, and from the subpackage it is listed under. Import from the package root in application code; the subpackage paths are where each name is defined. Kernel names these views read - ServiceSpec, dispatch, the refusals - are documented on the kernel's site.

    Settings¶

    This package defines none. The argument reader reads one of the kernel's:

    • SERVICE_SPECS_MAX_ARRAY_LENGTH: the longest list an array parameter with no max_length of its own takes. It is the kernel's key, read by the kernel, and keeps its name here. See how long a list may be.

    Pages¶

    SpecFormView ¶

    Bases: SpecPageBase

    A ServiceSpec validated by a form, served as the page a person fills that form in on.

    The spec's Validator must be a FormValidator, and its form class is the page's form:

    urlpatterns = [
    path(
        "books/new/",
        SpecFormView.as_view(spec=add_book_spec, success_url=reverse_lazy("books")),
    ),
]

    GET renders template_name with an unbound form under form, beside view and spec: the names Django's FormView uses, with extra_context merged in as Django's ContextMixin does. The spec's class-level permission check runs first, through authorize, so a page is never offered to a principal the post would refuse.

    The page's template is optional. template_name is django_spec_html/spec_form.html by default, a template this package ships: a plain document with no stylesheet, script or htmx attribute, holding the target pane, an unmet affordance's reason with the form disabled, and the form - its errors, a question's message and the field it asks for, and a submit button posting commit_button's name where one is set - inside a POST form with its token. It is found as any app's templates are, so a project lists django_spec_html in INSTALLED_APPS with APP_DIRS on, and as_view() refuses a page rendering it that no template engine finds. Its form is a file of its own, django_spec_html/spec_form_fragment.html, which the page includes and an htmx request is answered with, on every Django. Override either file the Django way, with one of the same name in a template directory found first, or django_spec_html/base.html, the document every shipped page extends; or set template_name to a page of the project's own.

    An update's page shows the row it updates. Every GET then finds its target as dispatch would, through resolve_target on the route's kwargs, coerced as a post's are: the row or set a target selector resolves, or None for a create. A check refusing it - the object-level check on a row, the scope check on a set or on None - raises PermissionDenied, as the post would be refused; a missing row or a selector's ServiceNotFound raises Http404; and a route value the spec's parameters refuse raises Django's BadRequest. The form shows a row's values for its own fields: a ModelForm of the row's model is built on a copy of it, as the Validator binds one, and any other form takes the row's values for the enabled fields it names as its initial. So a file the row holds is shown, with the clear checkbox an optional file's ClearableFileInput offers beside it. A create, a collection target and a missing row allow_none lets through show an empty form.

    POST starts as GET does: the route first, then that check, and only then is the form built from the post. A refused post is answered with the page again, and dispatch's shape check comes before its own permission check, so without it a principal the spec refuses would be shown the page - every row a choice field lists, and extra_context - by posting a malformed form, and a form whose constructor reads rows would read them for that principal. The Grant it returns goes to dispatch, so the class-level check runs once.

    Then the post finds its target, as GET does, before the form is built or read, so the form a refused post re-renders is built on the row as the page's was, its held file and clear checkbox shown. The target answers before the shape check: the object-level and scope checks and a missing row refuse a malformed post as they would a well-formed one, rather than dispatch re-rendering the page for a principal the row refuses. Dispatch is handed the target and the grant resolve_target returns, so it looks nothing up again and asks no check twice. A route value the target's reads refuse is left to dispatch, whose one refusal carries it beside the form's own.

    POST binds the form to the post and reads the arguments through its own widgets - a checkbox is True or False, a multi-select a list - because that is how Django reads a form, and a flat reading refuses a checkbox's "on". Only the form's fields are read, so the CSRF token and a named submit button never become arguments, and a disabled field is not read at all, as the form ignores what is posted for it. A field left blank is absent, as it is to the form. A number, date or date-time the field reads in one of its input formats - 10/25/2006, a localized 12,50 - is sent on in the form the shape check reads, through the field's own to_python, so the shape check never refuses what the form accepts. The URL kwargs are merged last, so the route wins a clash, as in request_arguments. Each is an argument, so the spec declares each one: a kwarg it does not is the host's misconfiguration, raised as ImproperlyConfigured under either unknown_arguments policy rather than answered as a refused post. Then dispatch:

    • A success redirects to get_success_url(result): success_url through Django's resolve_url by default, so a reverse_lazy or a URL name works, and a subclass overrides it to read the result. A view naming redirect_field_name - "next", as Django's LoginView names it - redirects instead to the URL the post or its query carries under that key, where get_redirect_url() finds it safe, so a page linked to from a list returns to the list.
    • A refusal of the arguments - InvalidArguments, or a ServiceValidationError - re-renders the bound form at 400 with the refusal placed on it by add_argument_errors. A service's string or list detail is about the whole form.
    • Any other refusal re-renders it with the message as a non-field error: ServiceConflict at 409, any other ServiceError at 422, UnsupportedMediaType at 415, any other DispatchError at 400. The statuses are error_response's, read from the one map, so a client reading a refused post - Turbo, which will not render a failed post answered 200 - reads it the same way.
    • A question, AdditionalInputRequired, re-renders it at 422, the message as a non-field error, as the confirmation page below.
    • NotPermitted and PrincipalUnavailable raise Django's PermissionDenied, and a not-found result or ServiceNotFound raises Http404, for the host's own 403 and 404 pages.

    The confirmation page is an AdditionalInputRequired rendered. Its schema is checked first by the kernel's check_requested_input, with the call's seeds, so a question no route could hear answered - a key no parameter declares, one a seed fills, a shape a transport cannot render, a type the parameter refuses - raises ImproperlyConfigured on the page and in the fragment alike, and is never rendered. Then the bound form is re-rendered with every value posted, and the context carries requested_input: the message, the schema, and the fields, the form's bound fields the schema names. The page builds no widget from a schema. The answer is a field the spec's form declares, an optional BooleanField whose absent box cleans to False, and asked_fields holds it back until a question names it: it is taken out of the form each GET and every other refusal renders, so it posts nothing of its own, and shown empty when asked, so a yes is never carried over to a question asked again. A key no field declares is asked by the message alone. The target is found and a set counted again for the post that asked, so the page says what it found then.

    Two wrappers, one outcome. The view decides what a request ends in once - a success, or the refusal's Outcome - and only then reads who asked, to choose how to answer it. Every request gets the page above unless wants_fragment says htmx asked for less, and then the same outcome is answered as a fragment, at the same URL:

    • The form renders get_fragment_template_names() where the page renders template_name, from the same context: on GET, and on every refusal the page re-renders, at 200 rather than the page's 4xx, since htmx swaps no 4xx by default. A shipped page's is its fragment file. For a page of the project's own the default address is <template_name>#spec-form, a {% partialdef %} inside the page's own template, which Django 6.0 resolves; below it, django-template-partials does, with its tag named in TEMPLATES as a builtin ("builtins": ["template_partials.templatetags.partials"]) and its loader around the project's. A template with no fragment at the address is Django's TemplateDoesNotExist naming it, never the page, which swapped into a form's target would nest a second layout inside it.
    • A success is fragment_success(result): HX-Redirect to get_redirect_url() or get_success_url(result), or the spec-result fragment in place.
    • A denial is raised in both modes alike, for the host's handlers.

    Both wrappers set Vary on the three headers the choice reads. No htmx header reaches dispatch: the arguments are the form's fields and the route's kwargs whichever wrapper answers, so a spec cannot tell the two apart. One header is read before dispatch, HX-Trigger-Name, and only to stop a post committing and, on a post that does not commit, to say which errors a refresh validated under validate_on_refresh shows, both below.

    A post that does not commit. A form that refreshes a dependent choice, adds a row or searches posts without meaning to run the operation. commit_button names the submit button whose post commits; None, the default, commits every post. Once set, commits(request) decides: a post whose data does not carry that name, or an htmx request whose HX-Trigger-Name names another control the post carries, is the page GET renders, admitted and with its target, its affordances and asked_fields held back as GET's are, but with the form bound to the post and built through form_kwargs as every form is, so a choice its constructor narrows by a posted value is narrowed again. Nothing is dispatched and nothing validated: the form shows no error, and the context carries refreshed, absent from every other render. It answers 200 on the page, and the form's fragment at 200 under htmx.

    Validating a post that does not commit. validate_on_refresh shows on such a post what its commit would refuse, so a field is checked as a person leaves it. The post is read as a commit reads it, the binding laid over it, and bound through the kernel's bind_arguments with the principal, the target the page found, the request's seeds and its call context: the shape check and the Validator, and nothing dispatched, no success_message sent. Its refusal is placed on the form as a refused commit's is, at 200 still, with refreshed in the context. Where HX-Trigger-Name names one of the form's fields, as its html_name, the name it posts under, only that field's errors are placed and no non-field error; on every other refresh, the whole refusal. It runs no provider, as bind_arguments runs neither input_data nor kwargs: a field the spec's input_data fills is judged as posted, so a required one left blank is refused by the refresh and accepted by the commit, which the provider fills.

    A success message. success_message, where it is set, is sent through django.contrib.messages on every success - the redirect, the HX-Redirect and the result fragment alike - formatted by get_success_message(result), % with the form's cleaned data as Django's SuccessMessageMixin formats it. Without the messages middleware it is skipped, and never raises MessageFailure. A refusal, a confirmation page and a post that does not commit send none.

    The request is read through the same attributes and hooks as SpecView's, checked by the same code in http/utils.py: route_kwargs says which URL kwargs fill which parameters; get_pool_seeds(request), asked once per request, answers the seeds the class-level check, the target's lookup and its object-level or scope check, the form's form_kwargs, the affordances and dispatch are handed, each resolving only the seeds it names; and get_server_arguments(request) answers the binding, laid over the route's arguments before the target is found and over the post's before dispatch. A field of the page's form the binding binds renders disabled with the server's value, and one it withholds disabled and empty, so the post never reads it. A named seed is resolved again at each step that names it, since a Grant carries no values: a resolver answering a fresh object answers each step a different one.

    The page's form is the Validator's, built with what its form_kwargs answers, through the kernel's form_keywords: on GET, on a refused post and for its own validation below, with the principal, the request's seeds, the row the post acts on and the request's one call context, the very dict dispatch is then handed. So a form whose __init__ takes a keyword - a queryset scoped by a tenant - is served, and the page's form offers the choices the Validator's accepts.

    One call context per request: a plain dict the page creates for the request and hands, as the same object, to every kernel call it makes - the class-level check, the target's lookup and its checks, the affordances, the form's keywords and dispatch - so a check, a condition or the service declaring call_context reads what an earlier stage put there.

    GET asks the spec's affordances once the target is found: the callable conditions always, through the kernel's unmet_operation_affordance on a pool built from the call's seeds, and, with none of those unmet and a row to ask about, the conditions on the row, as dispatch asks them. The first unmet Affordance is in the context as unavailable, for a template to read its code and reason; it is absent when every condition is met. The POST is unchanged, and dispatch's 409 stays the authority. A refused post's context carries code, the ActionUnavailable's, for a refusal carrying one, as error_response puts it in the JSON body; it is absent for every other.

    The page shows its target, on GET and on every refused post it re-renders, in the context beside the form: target is the row an instance selector found, or the set a collection_selector_spec resolved, and it is absent for a create and for a missing row allow_none lets through. A set comes with target_count, how many rows it held, and target_counted_at, when it was counted (django.utils.timezone.now()), so a template says "117 rows matched at 14:02" rather than promising a number the confirming post may not find. An empty set is no refusal: its scope check is asked, and the page counts 0. A queryset is counted by a COUNT on a fresh clone, never by reading its rows; the post re-runs the service on the set as it is then, and a refused one is counted again. A successful post counts nothing.

    target_display is the target as a person reads it, on a page that sets display_target. It is off by default: an Output describes what the operation returns, which need not be its target, so a page presents its target only where it says the Output describes it. On, the target is presented through the spec's presenter - its own, or its output selector's - with the context dispatch hands it, projected by the kernel's project_payload, and with every HANDLE dropped as well as every HIDDEN one. A row's is a dict of its fields, with label, the value of the field marked LABEL, beside them where there is one, and pairs, the same fields as name and value in order, for a template to loop over, since fields.items reads a field named items; a set's is a list of those, one per row, for at most target_display_limit rows, read in one query. as_view() refuses a page displaying its target whose spec has no Output, whose Output marks none of its own fields with a FieldMarking, or whose markings the kernel's projection refuses, such as two labels. Whether the Output describes the target's rows is known only once one is presented: an Output that does not raises on the page's first request, which is the cost of turning the display on.

    A refusal of the arguments shows every error in one post. Beside an InvalidArguments, the page's own form - built as the Validator's is, with the same keywords - is validated too, and the refusal is placed beside what it found, never twice. So after a shape-check refusal - a required field left blank, a date that does not parse - the form's further checks, a length, clean() or uniqueness, answer in the same post rather than the next. It is validated as the Validator validates its own, under the kernel's clean_held_to_their_columns, so a value no column holds - a key past 64 bits - is refused in the field's words and never reaches the database driver. A post whose route the target's reads refuse never found its row, so its form is not judged as one and carries the refusal alone. Any other refusal is no verdict on the arguments - a conflict, a service's own rule, an unavailable action - and the page's form carries it alone, validated no further.

    A partial spec's page renders no HTML required attribute, so the browser sends a post that leaves fields blank, and a blank field is absent: on a partial call, one the operation leaves as it is. A post with every field blank dispatches with no arguments but what a checkbox or a multi-select always sends, and is not refused. Beside a shape-check refusal, a partial page's form carries the refusal alone: its Validator takes the fields a post leaves out off its own form, and the page's form, validated whole, would call each one required.

    as_view() refuses, when the URLconf is imported, a view with no ServiceSpec, a spec whose Validator is not a FormValidator, a many spec, whose list of rows no form posts, a view with no success_url that does not override get_success_url, a commit_button that is not a button's name or is one of the form's fields, and a redirect_field_name that is not a key's name, is one of the form's fields or is the commit_button.

    Sync only, in this release. CSRF is the host's middleware, as for any Django view, and the template renders {% csrf_token %}.

    Attributes:

    Name Type Description
    spec ServiceSpec | None

    The operation served. Required.
    template_name

    The page's template, as for any Django template view: django_spec_html/spec_form.html, the one this package ships, by default.
    success_url Any

    Where a successful post redirects, read by get_success_url: a path, a reverse_lazy, or a URL name.
    pool_seeds PoolSeeds

    The seeds the spec's callables are resolved with, unless get_pool_seeds answers others for a request.
    unknown_arguments UnknownArguments

    What becomes of an argument no parameter declares.
    route_kwargs Mapping[str, str | None] | tuple[str, ...] | None

    Which URL kwargs fill which parameters: None for the strict rule, a mapping from a captured name to the parameter it fills or to None to drop it, or a tuple of names to allow, as route_arguments reads it.
    server_arguments ServerArguments | None

    The kernel's ServerArguments the server answers for, checked at as_view(). Its values may vary per request, through get_server_arguments, and its names may not.
    fragment_template_name str | None

    The template an htmx request's form is answered with, for a fragment in another file or under another name; None, the default, addresses <template_name>#spec-form, or a shipped page's own fragment file.
    display_target bool

    Whether the context carries target_display, the target presented through the spec's Output and projected by its markings: False by default, checked at as_view().
    target_display_limit int

    How many rows of a set target_display projects, the first that many in the set's own order: a positive int, 10 by default, checked at as_view(). target_count counts them all.
    asked_fields tuple[str, ...]

    The fields of the form held back until a post's AdditionalInputRequired asks for them by name: a tuple of optional, enabled fields the server does not answer for, checked at as_view(). Empty by default, so every field is shown.
    commit_button str | None

    The name of the submit button whose post commits, read by commits: None, the default, commits every post; a non-empty string no field of the form declares, checked at as_view().
    redirect_field_name str | None

    The key a post or its query carries the URL a success returns to under, read by get_redirect_url: None, the default, reads none; a non-empty string no field of the form declares and the commit_button is not, checked at as_view(). The page's context carries it, with the URL as next, for a refused post to send again.
    validate_on_refresh bool

    Whether a post that does not commit shows what its commit would refuse, bound through the kernel's bind_arguments and never dispatched. False by default, which shows no error. A page with no commit_button commits every post, so it has nothing to refresh.
    success_message str

    The message a successful post sends through django.contrib.messages, formatted by get_success_message with the form's cleaned data. Empty by default, which sends none.

    dispatch ¶

    dispatch(request: HttpRequest, *args: Any, **kwargs: Any) -> HttpResponseBase

    Django's dispatch, every answer varying on the headers the wrapper is chosen by.

    Here rather than in either wrapper, so a 405 and a success redirect vary too. A denial is raised, so the host's 403 or 404 page sets its own headers.

    get_pool_seeds ¶

    get_pool_seeds(request: HttpRequest) -> PoolSeeds

    The seeds this request's call is resolved with: pool_seeds unless overridden.

    Read once per request and handed to every step that resolves a spec callable: the class-level check, the target's lookup and its object-level or scope check, the form's form_kwargs, the affordances the page asks about, and dispatch; on a selector page, the class-level check and dispatch. Seed what the request carries rather than the request itself, as on SpecView: a spec callable naming request is handed this request here, and None on every reader that has none. A seed's resolver may name request or view and is handed this request and this page (test_a_seed_resolver_reading_the_request_binds).

    get_server_arguments ¶

    get_server_arguments(request: HttpRequest) -> ServerArguments | None

    The values the server answers for on this request's call: server_arguments unless overridden.

    The names it binds and withholds are the declared server_arguments' own, which as_view checked; only the values may vary per request, and the kernel's apply_server_arguments checks each on every call.

    wants_fragment ¶

    wants_fragment(request: HttpRequest) -> bool

    Whether request is answered with a fragment rather than the page.

    An htmx request is, unless it is boosted or a history restore: a boosted link or form swaps the whole body, and a history restore after a cache miss needs the whole page back, so both get the page. Read from django-htmx's request.htmx where its middleware set it, and from the three headers where it did not, so a host with django-htmx and one without get the same answer. Override it for another rule; the headers every answer varies on stay these three.

    Each condition, on each path, is held by its own row: test_read_from_the_headers (htmx-false, boosted, history-restore) and test_read_from_django_htmx_where_its_middleware_ran (not-htmx, boosted, history-restore), whose headers say the opposite of the details, so reading the wrong one fails it.

    get_fragment_template_names ¶

    get_fragment_template_names() -> list[str]

    The templates a fragment renders: fragment_template_name, or each page's #<fragment_name>.

    The default addresses a {% partialdef %} inside the page's template, named by fragment_name: spec-form on a page that posts, spec-results on a selector page. So turning htmx on is a template change. The tag and the #name address are Django 6.0's. Below it they are django-template-partials', configured in TEMPLATES with its tag as a builtin, "builtins": ["template_partials.templatetags.partials"], and its loader around the project's: installed as an app alone, it wraps the loader and the page fails to parse at {% partialdef %}. Without either, the default is a TemplateDoesNotExist naming it.

    A page this package ships is the exception: its fragment is a file of its own, which the page includes, so the fragment is that file on every Django (test_the_shipped_page_s_fragment_is_its_own_file). A project overriding a shipped page's file keeps the shipped fragment, and overrides the fragment's file to change it.

    as_view ¶

    as_view(**initkwargs: Any) -> Callable[..., HttpResponseBase]

    Django's as_view, then the spec, the redirect and the request hooks checked, once, for every request.

    The spec and the redirect first, so a view with no spec is refused as one whatever else it sets. Then the checks SpecView makes of the same attributes, by the same code: both hooks plain def, route_kwargs naming only parameters the spec declares and no bare string, server_arguments through the kernel's check_server_arguments against the declared pool_seeds, and no route kwarg filling a name the binding answers for. The page's own checks last, so a page reads route_kwargs and server_arguments already known to be well formed.

    get ¶

    get(request: HttpRequest, *args: Any, **kwargs: Any) -> HttpResponse

    The page, with an unbound form showing the target row, for a principal admitted to it.

    post ¶

    post(request: HttpRequest, *args: Any, **kwargs: Any) -> HttpResponse

    Dispatch the posted form: a redirect on success, the form re-rendered on a refusal.

    A post commits refuses is the page again, its form bound to the post, and nothing is dispatched.

    get_context_data ¶

    get_context_data(**kwargs: Any) -> dict[str, Any]

    Django's context - view, and extra_context - with the spec served, and the way back.

    Where get_redirect_url() answers a URL, the context carries redirect_field_name, the key it was read from, and next, the URL, so a page posting back to itself can send it again: the shipped templates render both as a hidden input. Two fixed keys, where Django's LoginView puts the URL under the field's own name, so a name such as errors or target never overwrites what the page renders. Both are absent where there is no URL to hold, an unsafe one included, so an unsafe value is never written back into the page (test_without_a_safe_value_neither_key_is_there).

    get_redirect_url ¶

    get_redirect_url() -> str

    SpecSelectorView ¶

    Bases: SpecRequestBase

    A SelectorSpec served as a page: a list's rows a page at a time, or one row.

    The read side of the pages: what a person browses, filters and picks a row from, declared once on the spec every other reader serves too. A LIST spec is a list page and a RETRIEVE spec the page of one row:

    urlpatterns = [
    path("books/", SpecSelectorView.as_view(spec=books_spec)),
    path(
        "books/<int:pk>/",
        SpecSelectorView.as_view(spec=book_spec, route_kwargs=("pk",)),
    ),
]

    It is a spec's read page, not a model's list view: what it lists, who may see it, which filters it takes and what may be done to each row are the spec's, and the page adds only the paging and the wrapper.

    GET, and HEAD, which Django answers by the same handler, are the methods it answers; anything else is 405. A request is:

    1. admitted, as every page admits it: the route checked against the spec's parameters, then the principal the class-level check admits, a denial raised for the host's 403 or 404 page;
    2. read by request_arguments' query-string branch - the URL kwargs under route_kwargs, the names server_arguments answers for dropped and then bound - as the JSON views read it, so a list page and a JSON list read each value the same way. A key the spec does not declare is ignored here, where the JSON views refuse it (see unknown_arguments). On a list, the paging keys are taken off first, so ?page=2 never reaches the spec;
    3. dispatched by the kernel's dispatch, with the grant the admission made, so the class-level check is asked once;
    4. rendered with the raw rows dispatch answered, and no present(): a template reads the rows themselves.

    The context. Beside view and spec:

    • rows: the rows served, a list. On a list page they are the page's rows, read in one query; on an instance page, the one row, or none for a RETRIEVE with allow_none that found nothing.
    • row: the one row, on an instance page that found one.
    • page: on a list page, the kernel's OutputPage - page, limit, total, total_pages, has_next - its items the same list as rows, so a template reading either reads no row twice. previous_page_query and next_page_query, where those pages exist, are the query the page read with the page key replaced, every filter kept, for a link's ?.
    • filter: the spec's filter_set, a django-filter FilterSet, bound to the query for display only, where the spec declares one.
    • table: table_class built over rows, where it is set.
    • row_displays: with display_rows on and no table_class, each row as its Output marks it for a person - label, fields and pairs, as the form page's target_display - with the raw row itself as row, so a template shows the one and asks available of the other.

    Each row carries its affordances. Dispatch answers every row's affordances in bulk, as the spec's affordances declare them, and the page reads each row's answers once, so {% load django_spec_html %} and {% if row|available:"rename" %} asks a row what the operation's own dispatch would enforce, in no query of its own. See available.

    Paging. A list is paged by the kernel's paginate_output: the page named by page_kwarg, paginate_by rows to a page, never more than max_page_size. A page that is not a whole number is page 1, and one past the last is the last, rather than a refusal: a public page clamps a link someone edited, and the page served says which it is. A client chooses the page size only where page_size_kwarg names the key it sends, bounded by max_page_size, which as_view() then requires; a value that is not a whole number is paginate_by, and a whole number below one is a page of one row, as paginate_output clamps it.

    The query a page reads is get_query(request), the request's own query string unless a subclass answers another: a list that opens where the last visit left it reads a query the host kept in the session. The paging, the filter form, the spec's arguments and the links all read that one answer, and the template's request carries it as GET.

    The filters are the spec's. filter.form is the FilterSet's form bound to the query for display, its own validation never run: dispatch reads the query, through the filter set's parameters, and is the one reader that decides, since two readers of one query string could disagree - django-filter's comma-separated filters split a value their own way.

    A refusal is the page again, at the status of the one map: an argument refusal at 400, a precondition's ServiceError at 422, and so on, with errors, every message the refusal holds as a string, a message about a parameter prefixed with its path, and code for a refusal carrying one. The refusal is placed on filter.form too, an argument refusal at the fields it names. A denial is raised, for the host's 403 or 404 page, and a RETRIEVE that finds no row is Http404.

    The fragment. An htmx request, unless boosted or a history restore, is answered with the results alone, at 200 whatever the outcome, as every page answers a fragment: fragment_template_name, or the spec-results fragment of template_name, or the shipped page's own fragment file. Every answer varies on the three headers that choice reads. A filter form's hx-get answered with it is a live search, and a next-page link's is a load-more.

    A django-tables2 table is composed, never imported. table_class is built with the page's rows and order_by=(), so the table neither pages nor orders them: the spec ordered them, and paginate_output paged them. Its columns are not orderable unless table_order_by_field names the spec's own ordering parameter, which a header link then sets, for dispatch to read like any filter.

    The page's template is optional: django_spec_html/spec_selector.html by default, which this package ships, its results in django_spec_html/spec_selector_fragment.html. It renders the filter form's fields, the table or each row's display, and the previous and next links. Found, refused at as_view() and overridden as SpecFormView's is.

    as_view() refuses, when the URLconf is imported, a spec that is not a SelectorSpec and does not compile to one; the request hooks as every page refuses them; paging attributes of the wrong type, a client page size with no ceiling, and a list spec declaring a parameter under a paging key, whose value could never reach it; a table_order_by_field the spec does not declare, since no header link would then sort the rows; and display_rows on a spec whose Output cannot display a row.

    @admin.register(Book)
class BookAdmin(SpecActionsMixin, admin.ModelAdmin):
    spec_actions = (
        SpecAction("withdraw", withdraw_book_spec, "Withdraw", parameter="pk"),
        SpecAction("publish", publish_books_spec, "Publish", parameter="pks"),
    )

    Which kind of action is the spec's target's answer. A spec with an instance_selector_spec is an object action: a link among the change page's object tools, to <object_id>/actions/<name>/, whose object_id fills the selector's parameter through the page's route_kwargs, unquoted as the admin quotes it. A spec with a collection_selector_spec is a changelist action: an entry in the action dropdown, which redirects to actions/<name>/ with the selected rows' primary keys in the query string, repeated under parameter. The page binds them to that parameter as server_arguments, read from the query string on GET and on the post the page sends back to its own URL, so nothing posted stands in for the selection; and the collection selector still decides the set, so a key it does not answer is not acted on.

    The admin's scope comes first, as for its own actions and its change page: a page is served only to a principal holding the admin's view or change permission, the row's on an object action, and acts only on rows in the admin's get_queryset(). An object action's row outside it is a 404, and a changelist action's selection is narrowed to it before it is bound, so a key outside it never reaches the selector. Within that scope the spec's own checks run, and its selector decides the set.

    Each page is the spec's own: SpecFormView for a spec validating with a FormValidator, SpecConfirmView for one with none, built once when the admin is registered, so as_view() refuses then what it refuses of any page. Its URL is added by get_urls() ahead of the admin's own, wrapped in admin_site.admin_view(), so only a signed-in staff member the site admits reaches it; the page then admits the principal by the admin's permission and the spec's own checks, as on any route, and answers the rest with the host's 403 page. Its templates, django_spec_html/admin/spec_form.html and django_spec_html/admin/spec_confirm.html, extend admin/base_site.html with the admin's breadcrumbs and title around the very fragment the shipped page includes, so an htmx request is answered with that fragment, as on any page. A success returns to the row's change page or to the changelist, with the page's success_message among the admin's messages.

    Offered only to a principal both admit. The object-tools link and the dropdown entry are shown only where the kernel's authorize, the spec's class-level check, admits the request's principal, asked with the page's own seeds and call context, and the admin's view or change permission does too. The admin's model permissions say nothing about the spec's, so they are not the whole gate: the spec's checks are asked as well, and the page asks both again, the object-level ones included, on every request. An entry not offered is not in get_actions(), which the changelist reads again on the post that runs an action, so posting its name runs nothing.

    The change page is rendered from django_spec_html/admin/change_form.html, which extends admin/change_form.html and lists the links ahead of the admin's own tools: a ModelAdmin setting a change_form_template of its own extends that template to keep them.

    ImproperlyConfigured is raised when the admin is registered for a declaration that is not a SpecAction, a name that is not a slug, is used twice or is one of the admin's own URL names, a label that does not format with the model's names, a spec that is not a ServiceSpec, a many spec, a spec with no target, a parameter its target selector does not read or, on a changelist action, one that is not an array, and a page_kwargs key the mixin answers for.

    JSON views¶

    SpecView ¶

    Bases: SpecViewBase

    One spec as a view: each request it answers goes through dispatch_request.

    Every attribute can be set on a subclass or passed to as_view():

    urlpatterns = [
    path("notes/", SpecView.as_view(spec=list_notes_spec)),
    path("notes/<int:pk>/rename/", SpecView.as_view(spec=rename_note_spec)),
]

    The methods follow the spec. A SelectorSpec answers GET and HEAD, a ServiceSpec POST, and methods replaces that with the ones it names, from GET, HEAD, POST, PUT, PATCH and DELETE. Any other method is Django's own 405, whose Allow header lists exactly the methods served, and OPTIONS is Django's own answer. The URL kwargs are arguments, merged last so the route wins a clash, which means the spec declares each one: a route capturing a kwarg its spec does not declare raises ImproperlyConfigured on the first request it serves, since that is the host's configuration rather than anything a client sent. route_kwargs renames or drops the kwargs a spec does not declare, as an include() prefix such as <org>/ needs.

    The request reaches the call through two hooks, each defaulting to the attribute of its name: get_pool_seeds(request) for the seeds, so a tenant or a locale middleware resolved reaches a permission check, a selector or a Validator; and get_server_arguments(request) for the values the server answers for, which outrank whatever the client sent and whose names are the declared server_arguments' own. The view passes itself to dispatch_request as view=, so a spec callable naming request or view is handed this request and this view.

    as_view() checks the configuration when the view is built, so a view with no spec, an async def hook, route_kwargs naming a parameter the spec does not declare or one the binding answers for, or a binding that cannot mean what it says, fails when the URLconf is imported rather than on its first request. Each request checks what only it can show: a captured kwarg the spec does not declare or the binding answers for, two kwargs filling one parameter, and the hooks' answers (see SpecViewBase.as_view).

    CSRF is the host's middleware, as for any Django view. Nothing here is exempted, and csrf_exempt(SpecView.as_view(...)) is one line for a host that wants it.

    AsyncSpecView ¶

    Bases: SpecViewBase

    SpecView, with every handler async.

    The same attributes, methods, checks and answers, through adispatch_request. Django serves a class-based view async only when every handler it defines is async def, and refuses a class that mixes the two, so every method a spec may be served on is async here, not only the ones it answers by default. Under ASGI this keeps the request off a worker thread until the kernel needs one; under WSGI Django runs it in an event loop of its own, which costs more than SpecView and buys nothing.

    get_pool_seeds and get_server_arguments stay sync methods, run in an executor hop of their own before dispatch, so an override reading request.user or a model is never a query on the event loop. as_view() refuses an async def one, which would never be awaited.

    Not a subclass of SpecView, for the same reason: an async handler cannot stand in for a sync one.

    dispatch_request ¶

    dispatch_request(
    spec: ServiceSpec | SelectorSpec | SpecSource,
    request: HttpRequest,
    *,
    url_kwargs: Mapping[str, Any] | None = None,
    route_kwargs: Mapping[str, str | None] | tuple[str, ...] | None = None,
    server_arguments: ServerArguments | None = None,
    success_status: int | None = None,
    grant: Grant | None = None,
    pool_seeds: PoolSeeds = DEFAULT_POOL_SEEDS,
    unknown_arguments: UnknownArguments = UnknownArguments.REJECT,
    view: Any = None,
) -> HttpResponse

    Dispatch spec for request and answer it as JSON: the function a view calls.

    1. The principal is request.user, anonymous included, since the spec's permission check is what decides whether anonymous may act. An authenticated user whose is_active is false is refused as PrincipalUnavailable: a backend other than ModelBackend can log one in, and a deactivated principal never acts. Dispatch refuses one by the same rule; refusing here as well keeps the request unread for it.
    2. The arguments are request_arguments for spec.parameters(), with url_kwargs merged last under the names route_kwargs maps them to, and server_arguments applied over them by the kernel's apply_server_arguments: its bound values outrank whatever the client sent, and its withheld names are dropped. A URL kwarg filling one of its names is refused, as the host's misconfiguration. The binding is not checked here: a host's own view calls check_server_arguments once, when it is built, as SpecView.as_view() does.
    3. dispatch, with grant, pool_seeds and unknown_arguments as given, and a call context of its own holding request and view. So a spec callable naming request - a seed's resolver, a selector, a permission check, an affordance condition, a form_kwargs, the service - is handed this very request, and one naming view is handed view: the host's own view, which passes itself, as SpecView does, and None where it passes nothing (TestTheRequestAndTheView in test_dispatch_request).
    4. The answer. A not-found result is 404 with a detail. Otherwise the presented value, bare, at success_status if given, else 204 for a service with nothing to present and 200 for everything else - the defaults djangorestframework-services answers with. A 204 has no body.

    A refusal of either family, from any of the four steps, is answered by error_response. Anything else propagates, a configuration error included: it is wrong for every caller, so it belongs to the host's error handling rather than to one client's response. A URL kwarg spec does not declare, and that route_kwargs neither renames nor drops, is one, raised as ImproperlyConfigured: every URL kwarg is an argument, and the route is the host's. So is a bound value its parameter refuses: the client neither sent it nor can see it.

    spec may be a SpecSource: it is compiled once, first, and every step reads the spec it compiles to.

    CSRF is the host's middleware, as for any Django view: nothing here exempts a view, and csrf_exempt is one line for a host that wants it.

    error_response ¶

    error_response(exc: DispatchError | ServiceError) -> JsonResponse

    exc as JSON, at the status djangorestframework-services answers it with.

    One map for both families, at djangorestframework-services' statuses, and the one the page reads too. Two bodies differ from its answer. A service's string or list detail, which DRF answers as a bare list and this as a field map under non_field_errors, so every 400 here has one shape. And an AdditionalInputRequired schema, which DRF reads as an error detail and so writes with every value a string ("minimum": "1"), and this writes as the JSON Schema it is:

    Refusal Status Body
    InvalidArguments 400 the error tree
    ServiceValidationError 400 its detail, as a field map
    NotPermitted, PrincipalUnavailable 403 {"detail": message}
    ServiceNotFound 404 {"detail": message}
    ActionUnavailable 409 {"detail": message, "code": code}
    any other ServiceConflict 409 {"detail": message}
    AdditionalInputRequired with a schema 422 {"detail": message, "schema": schema}
    any other ServiceError 422 {"detail": message}
    UnsupportedMediaType 415 {"detail": message}
    any other DispatchError 400 {"detail": message}

    Every 400 body is a field map. InvalidArguments is its tree, whose integer row keys JSON writes as strings. A ServiceValidationError's mapping is its body as it is, and a string or a list goes under non_field_errors, where a message about the input as a whole sits in the tree too. A lazy translation is one message, not a sequence of characters, and renders in the active language: JsonResponse's encoder renders every lazy string it meets, messages included.

    Never 401. A session-authenticated view has no challenge to answer, and a 401 tells a client to start an authentication flow it has no way to finish. An anonymous caller a permission check refuses is a 403, like any other refused principal.

    Two members add a key beside detail, and keep their base's status. ActionUnavailable is a conflict, and its arm exists only to put the affordance's code in the body beside the detail a client already reads: the stable code is the whole point of the member, and a client left with only the sentence has nothing to branch on. AdditionalInputRequired is "I need one more value", which is the operation being unprocessable as asked, so it stays a 422 like any other service error; the schema naming what is missing joins the body, because without it a client is told that something is needed and not what. Only when there is a schema: the error is valid without one, and growing the body unconditionally would change every plain message into an object for no gain.

    A DispatchError no row names - raised by nobody in this package, or a subclass a later release adds - is still a refusal of the call rather than the operation's own verdict, so it answers 400 rather than 422.

    Reading a request¶

    request_arguments ¶

    request_arguments(
    request: HttpRequest,
    parameters: Parameters,
    *,
    url_kwargs: Mapping[str, Any] | None = None,
    route_kwargs: Mapping[str, str | None] | tuple[str, ...] | None = None,
    server_arguments: ServerArguments | None = None,
) -> dict[str, Any]

    The arguments a request carries for parameters, typed as a JSON caller would send them.

    Where they are read from depends on the method and the body:

    • GET and HEAD: the query string, which is flat. Any body is ignored.
    • Any other method, with an application/json body: the body, read as it is. It must be a JSON object; an empty body is no arguments, as DRF's parser reads one. Its values are not coerced here: a "5" sent for an integer is the shape check's to read, as it reads one from any caller.
    • Any other method, with a form body (application/x-www-form-urlencoded or multipart/form-data): the fields, which are flat. Django parses one into request.POST for POST alone, so a PUT, PATCH or DELETE body is parsed here the same way rather than arriving empty. Any other body is refused as UnsupportedMediaType rather than read as none, since an operation whose parameters are all optional would then run with nothing; a request with no body carries no arguments, whatever its Content-Type says.

    A flat source is read by the declaration, through the kernel's flat_arguments. A parameter of type array takes every value its key was sent with, and anything else takes the last, as QueryDict reads a repeated key. An array of numbers, integers, booleans or decimal strings also reads a value holding commas as its elements, ?ids=1,2 as [1, 2] with the space around a part trimmed, because a comma cannot be part of such a value and it is the spelling a django-filter CSV filter advertises; repeated keys and commas may mix. A decimal element stays the string it spells. An empty part (?ids=1,,2) is not dropped as a blank element is: it is refused at its index as any malformed element is. A string array is split only where its choices hold no comma, as an ordering's do, so ?o=title,-pk is ["title", "-pk"]; otherwise it is never split, since a comma is part of a string. An array is read no further than one element past the most it takes - its max_length, or the SERVICE_SPECS_MAX_ARRAY_LENGTH setting's default - so a list over it is refused at its name as a whole, without a million commas becoming a million elements first; Django's DATA_UPLOAD_MAX_NUMBER_FIELDS counts keys, and a comma list is one. A blank value is absent unless "" is one the parameter can take: a plain string can, and a number, a boolean, a date, a decimal, or a string whose choices leave the blank out cannot. A flat wire has no other spelling of "left blank", and an empty ?count= or ?since= from a filter form is not a refusal to count or a malformed date. Each blank element of an array is read by the same rule, the whole array absent once nothing is left. Django's csrfmiddlewaretoken is dropped. What remains goes through coerce_flat, which leaves an undeclared key as it is, so the closed argument set in dispatch stays the one place that refuses it, under the caller's policy.

    An upload is an argument, under the name its part carries, as each field is: the upload itself, Django's UploadedFile, for a parameter of type file, every upload under the name for an array, and the last of repeated ones for anything else. It replaces a field of the same name, since a browser sends a file input only as a file: a single value reads as the upload in DRF's merged data too, where an array there would hold the field and the uploads together. A POST's uploads are Django's own request.FILES; those in a PUT, PATCH or DELETE body are parsed here with its fields. An upload under a name parameters do not declare passes through like an undeclared field, for the closed argument set to refuse, and a file input left empty is no upload, so it is absent. Only a multipart body carries one.

    URL kwargs are merged last, through coerce_flat as well since a path segment with no converter is a string. The route wins a clash, as it does in djangorestframework-services: a client-supplied value must not move the route's scope, so /notes/4/ with pk=9 in its body is about note 4. On a flat request the two are coerced together, so every refusal comes back at once and a clashing client value the route replaced is never refused. route_kwargs says which URL kwargs fill which parameters, renaming or dropping the rest, as route_arguments reads it.

    Every name server_arguments answers for is dropped from what the client sent, before anything is coerced, so a client's ?owner=abc for a bound integer is never refused as the client's 400 for a name it was never offered. A URL kwarg filling one is refused instead, as the host's misconfiguration: the route is the host's, and it may not contradict the host's own binding, so a capture the spec should not read is dropped explicitly, with route_kwargs={name: None}. Only the names are read here: the values are laid by the kernel's apply_server_arguments, which needs the spec to check them, so a host's own view passes the result through it, as dispatch_request does.

    Raises:

    Type Description
    InvalidArguments

    a JSON body that does not parse or is not an object, under non_field_errors; or coerce_flat's refusals, each at its parameter's name.
    UnsupportedMediaType

    a body that is neither JSON nor a form.
    ImproperlyConfigured

    a URL kwarg parameters does not declare, a route_kwargs naming a parameter they do not, or a URL kwarg filling a name server_arguments answers for, which is the host's route rather than the client's request; see route_arguments.

    route_arguments ¶

    route_arguments(
    parameters: Parameters,
    url_kwargs: Mapping[str, Any] | None,
    *,
    route_kwargs: Mapping[str, str | None] | tuple[str, ...] | None = None,
) -> dict[str, Any]

    The kwargs a route captured, as arguments, each one a parameter the spec declares.

    How request_arguments reads the route, public so that a host's own view reading the rest of its arguments some other way - a bound form, a page's own fields - merges the route by the same rule and refuses the same misconfiguration.

    Every URL kwarg is an argument, so a route capturing one its spec does not declare is the host's configuration, wrong for every request the route serves, rather than anything a client sent. It is refused as one - Django answers it 500 and shows it under DEBUG - where a client's own undeclared argument is a 400. The unknown_arguments policy does not reach it: that policy is about what a client sends, and no client can send a route kwarg or stop sending one.

    route_kwargs says which kwargs fill which parameters, for a route whose kwargs are not all the spec's, as an include() prefix such as <org>/ reaches every view under it:

    • None, the default, is the strict rule above, unchanged.
    • A mapping from a captured name to the parameter it fills, or to None to drop it: {"note": "pk", "org": None}. A captured name the mapping does not mention is still held to the strict rule, so a typo in the route is caught as before.
    • A tuple of names is an allow-list: each passes under its own name, and every other captured kwarg is dropped.

    Every target a mapping names, and every name an allow-list lists, is a parameter the spec declares, checked whatever the route captured: the setting is the host's, the same on every route the view is mounted on. Two kwargs filling one parameter, a rename onto a name the route also captures, are refused as well, since neither could win honestly. A route kwarg is never a server value, whatever it fills: the client's URL chose it, so a malformed one is the client's 400, as anything a client sent is (test_a_renamed_kwarg_that_does_not_parse_is_the_clients_400).

    Returned as a plain copy and uncoerced, so each caller merges it last, where the route wins a clash, and coerces it beside what the client sent: coerce_flat(parameters, {**read, **route_arguments(parameters, url_kwargs)}), so one refusal carries every problem with either.

    Raises:

    Type Description
    ImproperlyConfigured

    naming every undeclared kwarg, target or allowed name, in order; or a parameter more than one kwarg fills.
    TypeError

    route_kwargs is a bare string, which would otherwise be read as a tuple of its characters.

    request_principal ¶

    request_principal(request: HttpRequest) -> Any

    request.user, anonymous included, unless it is a deactivated account.

    How dispatch_request, adispatch_request and both spec views read the principal, public so that a host's own view - one rendering a page, or reading its arguments some other way - reads it by the same rule, and refuses before it reads anything else of the request.

    Anonymous is passed through because a permission check is what decides whether anonymous may act, and the spec declares that check; refusing it here would make every spec's policy stricter than the one it states.

    A deactivated account is refused, by the rule dispatch itself applies and resolve_principal applies off HTTP: ModelBackend never logs one in, but AllowAllUsersModelBackend and a project's own backend may. The rule asks about authenticated users alone, since AnonymousUser.is_active is False, and a custom user model with no is_active reads as active. Dispatch would refuse the same user; refusing here as well is what keeps the request unread for one, as adispatch resolves a principal_id before looking at its arguments.

    Touching request.user evaluates the lazy object AuthenticationMiddleware leaves there, which is a session query, so an async caller calls this off the event loop, as adispatch_request does.

    Type Description
    PrincipalUnavailable

    an authenticated user whose is_active is false.

    add_argument_errors ¶

    add_argument_errors(form: BaseForm, detail: Mapping[Any, Any]) -> None

    Place a refusal tree on a bound form, beside the form's own errors, never twice.

    detail is an InvalidArguments tree, or a ServiceValidationError's mapping. Each message goes where a person reading the form looks for it, through Django's public form.add_error:

    • A key naming one of the form's fields puts its messages on that field. A form is flat, so the only tree below a field is an array's element indices, which mean nothing to a person reading one control: the messages go on the field without them.
    • non_field_errors, and Django's own "__all__", go to the form's non-field errors as they are.
    • Any other key - a URL kwarg such as pk, or a key a service chose - goes to the non-field errors prefixed with its path, "pk: ...", so the reader knows what it is about. A nested tree is flattened to its leaves with the path joined by dots, "books.1.title: ...", a row's own non_field_errors adding nothing to the path.

    Never a duplicate. A message the form already carries at the same place is not added again. The form validating the same data says the same thing the kernel does - a FormValidator's refusal is the form's errors, and the shape check spells its messages as Django's fields do - so without this most refusals would show twice. A form not yet validated is validated first, as reading form.errors would, so the form's own errors are always the ones compared against; but with the guards a FormValidator's form is validated with, since the form's own validation would hand the database driver a number no integer column holds, which SQLite's refuses with OverflowError. A model choice field's key past its column's range is refused as invalid_choice and a ModelForm's value past its integer column's range as max_value or min_value, in the words a FormValidator refuses them with, so the refusal of one is placed once (test_a_list_s_key_past_its_column_is_refused_once, test_a_model_form_s_integer_past_its_column_is_refused_once). A form already validated is compared as it stands.

    A leaf is a message whatever its type: a string, a lazy translation (which is not a str, and is never taken apart into characters), or a list of either. The form must be bound, as Django's add_error requires.

    Refusals¶

    UnsupportedMediaType ¶

    Bases: DispatchError

    A request carried a body that is neither JSON nor a form.

    Refused rather than read as no arguments. Read as none, a PATCH sent as text/plain or application/merge-patch+json to an operation whose parameters are all optional would run with nothing and answer success, which tells its client the change was made. A request with no body is not refused, whatever it is labelled, since there is nothing in it to misread.

    default_message is a msgid in the package's catalog, looked up in the active language each time a refusal is built with no message of its own. A message the caller passes is used as given.

    A refusal of the call rather than the operation's verdict, so a DispatchError, answered 415 as djangorestframework-services answers it.
