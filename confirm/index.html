    Confirming an operation¶

    A spec with nothing for a person to fill in, served as the page that confirms it: what the operation acts on, and a button. Withdrawing a book, archiving a note, closing every stale ticket. Every argument the operation takes comes from the server's side - the route, a pool seed, a kwargs provider or server_arguments - so the page posts nothing but its token and the button, and nothing a post carries becomes an argument.

    SpecConfirmView serves a spec whose Validator is None. It shares everything with SpecFormView but the form: the admission, the target and its display, the affordances, the fragment wrapper under htmx, the post that does not commit, the success and its message. Each works as Serving a page describes it, and this page says only where the two differ.

    from django_spec_html import SpecConfirmView

    Which view serves a spec¶

    The spec's Validator The view
    a FormValidator SpecFormView: the page is the form
    None SpecConfirmView: the page is the target and a button
    any other neither: a page renders no inputs it would have to guess

    Use SpecConfirmView when there is nothing to ask a person but yes. If the operation takes a value a person chooses - a reason, a date, a "yes, for good" box - declare a form that holds it and serve the spec with SpecFormView, whose asked_fields holds a confirmation back until the service asks for it. as_view() refuses, when the URLconf is imported, a spec with a Validator: a FormValidator's is pointed at SpecFormView, and any other is named.

    The example withdraws a published book. The route names the book, and there is nothing else to send:

    class IsSignedIn(PermissionCheck):
    message = "Sign in to withdraw a book."

    def has_permission(self, principal: Any, spec: Any) -> bool:
        return principal.is_authenticated


@dataclasses.dataclass
class BookOut:
    """A book as the operation returns it, and as its page names it."""

    pk: Annotated[int, FieldMarking.handle()]  # another call's input: never shown
    title: Annotated[str, FieldMarking.label()]  # the name a page calls it by
    status: Status


def book_by_pk(*, pk: int) -> QuerySet[Book]:
    return Book.objects.filter(pk=pk)


def withdraw(*, instance: Book) -> Book:
    instance.status = Status.DRAFT
    instance.save(update_fields=["status"])
    return instance


# No Validator: the route names the book, and there is nothing else to send.
withdraw_book_spec = ServiceSpec(
    service=withdraw,
    permissions=[IsSignedIn()],
    instance_selector_spec=SelectorSpec(
        kind=SelectorKind.RETRIEVE,
        selector=book_by_pk,
        reads=Parameters.of(Parameter("pk", "integer", required=True)),
    ),
    presenter=DataclassPresenter(BookOut),
    affordances=[
        Affordance(
            code="not_published",
            reason="Only a published book can be withdrawn.",
            when=Q(status=Status.PUBLISHED),
        )
    ],
)

    urlpatterns = [
    path(
        "books/<int:pk>/withdraw/",
        SpecConfirmView.as_view(
            spec=withdraw_book_spec,
            template_name="spec_confirm_view.html",
            fragment_template_name="spec_confirm_view_form.html",
            success_url=reverse_lazy("books"),
            # The parameter the route fills, which as_view() reads to know
            # that a post to this page needs to carry nothing.
            route_kwargs=("pk",),
            # BookOut describes the book withdrawn, so the page names it.
            display_target=True,
            commit_button="withdraw",
            success_message="Book withdrawn.",
        ),
    ),
    path("books/", books, name="books"),
]

    What the page renders¶

    GET renders template_name with the context every page builds - view, spec, target, a set's target_count and target_counted_at, target_display on a page that sets display_target, and unavailable when an affordance is not met - and no form. A key with nothing to hold is absent, as on every page, so a template's {% if form %} is false rather than {{ form }} rendering None. The template renders its own <form method="post">, the CSRF token and the submit button:

    <div id="withdraw">
  {% if target_display %}<p>Withdraw <strong>{{ target_display.label }}</strong>?</p>{% endif %}
  {% if unavailable %}<p>{{ unavailable.reason }}</p>{% endif %}
  {% if requested_input %}<p class="asked">{{ requested_input.message }}</p>
  {% else %}{% for error in errors %}<p class="error">{{ error }}</p>{% endfor %}{% endif %}
  <form method="post" hx-post="" hx-target="#withdraw" hx-swap="outerHTML">{% csrf_token %}
    <button name="withdraw"{% if unavailable %} disabled{% endif %}>Withdraw it</button>
  </form>
</div>

    The URLconf above renders it as the fragment under htmx, and inside this page otherwise:

    <html><body><h1>Withdraw a book</h1>{% include "spec_confirm_view_form.html" %}</body></html>

    Above, the page names the book by its LABEL. On a draft the button is disabled, with the affordance's reason above it. Dispatch still asks every affordance on the post, so a book withdrawn between the page and its post is refused at 409.

    The shipped template¶

    A template is optional. A view naming none renders django_spec_html/spec_confirm.html, which this package ships, with its target pane and button in django_spec_html/spec_confirm_fragment.html, the file an htmx request is answered with. It is found, refused at as_view() when no engine finds it, and overridden as the form page's is: list django_spec_html in INSTALLED_APPS with APP_DIRS on. It renders, escaped and with no stylesheet, script or htmx attribute:

    • the target pane: a set's count and when it was counted, and target_display where the page sets display_target, but never the target itself;
    • an unmet affordance's reason, with the button disabled;
    • a refused post's errors as a list, or a question's message alone, since no control is built from its schema; a refusal's code is the form's data-code;
    • the button, posting commit_button's name where one is set.

    What a post sends¶

    POST dispatches with the route's kwargs alone, read by route_kwargs and coerced by their declarations, with the request's seeds and the binding laid over them, as a form page's are. The post's own data is never read: not the CSRF token, not the button, not a key named like a parameter. A post carrying pk=7 to /books/3/withdraw/ withdraws book 3. So the closed argument set holds with nothing to check, and a post cannot fill a parameter the route, a seed or server_arguments fills, nor one nobody declared.

    commit_button works as on a form page: above, only a post carrying withdraw runs the operation, and any other post is the page again, with refreshed in its context.

    Every required parameter has a source¶

    as_view() refuses a spec demanding a parameter that only a post could supply, since no post to this page carries one. Which parameters the call demands is the kernel's answer, read through bind_arguments on a call carrying nothing: a parameter that is optional or declares a default is not demanded, and nor is a key a typed kwargs provider fills or may decline, or any read an untyped provider reaches. Each one left must be supplied by one of three sources, as they stand when the URLconf is imported:

    Source Supplies
    the route each parameter route_kwargs names a kwarg into: a tuple's names, a mapping's targets
    the seeds each name the kernel's server_owned_keys reads off the declared pool_seeds, such as a reflected read a registered seed fills
    the binding each name server_arguments binds a value to

    The route must say what it fills. as_view() is called while the URLconf is being built, before the pattern it is mounted on exists, so under the strict rule, route_kwargs = None, the route supplies nothing to this check. That is why the example names route_kwargs=("pk",). A mapping counts only the parameters it maps a kwarg into, so under {"org": None}, for an include() prefix, a pk the route still passes under its own name is not counted until it is mapped to itself: {"org": None, "pk": "pk"}. Without any:

    SpecConfirmView requires pk, which no post to a confirmation carries: fill each from the route, naming it in route_kwargs, or from a pool seed, a kwargs provider or server_arguments.

    A seed only get_pool_seeds adds per request is not seen either, since there is no request yet: declare it on pool_seeds. A name server_arguments withholds is refused by the kernel's own check_server_arguments first, in its words.

    A refused post¶

    A refused post is the confirmation page again, at the status of the one map, and needs no messages app: a button posted from another page lands on a page that works, and says why.

    • The page answers 400 for an argument refusal, 409 for a conflict or an unavailable action, 422 for any other service refusal, and under htmx the fragment at 200, as on every page.
    • The context carries errors, every message the refusal holds, as a list of strings in the refusal's order. With no field to put one on, a message about a parameter is prefixed with its path: a route value the target's reads refuse is "pk: Enter a whole number.".
    • code is there for a refusal carrying one, as on a form page, and the target is shown again.
    • A denial is raised for the host's 403 or 404 page.

    A success¶

    A success redirects to get_success_url(result), or under htmx answers HX-Redirect or the spec-result fragment, as on a form page.

    success_message is formatted with the target, % with a mapping whose one key is target, result.instance: "%(target)s was archived." names the row by its str(). A form page formats with the cleaned data, which with no Validator is {}. A set is the queryset, read when the message is formatted, so it holds the rows that still match once the operation has run. To name what the operation returned, override get_success_message(result) and read result.value. The message is sent where the messages middleware runs, and skipped where it does not.

    A question cannot be answered here¶

    A service raising AdditionalInputRequired is shown its question, and the page cannot answer it. The schema is checked first by the kernel's check_requested_input, as on a form page. Then the page is re-rendered at 422, or as the fragment at 200, with requested_input - the message and the schema - and the message in errors.

    The page builds no control from a schema, and no post is read for an answer, so a confirming post is asked again. With no Validator, an answer could only be a top-level parameter the spec reads, and reading one off the post would undo what the page is for:

    • every post carries the CSRF token and the button, so refusing undeclared keys needs a list of exemptions, and a box with no value posts "on", which a boolean parameter refuses;
    • the template would have to build the control from the schema, which no page does: on a form page, the form declares it;
    • and the post would become a channel filling a read on every post, not only the one a question asked.

    So an operation that asks a person something mid-flight declares a form that holds the answer, an optional BooleanField, and is served by SpecFormView with that field in asked_fields, as the confirmation page shows. A page with a target and a button is already the confirmation: a service that also asks on this route will ask forever.

    Not a gate on an agent route¶

    Neither the page nor a question is a security boundary. The spec is one declaration for every route, and on an agent route the same AdditionalInputRequired goes back to the model as a retry naming the missing argument, which the model can answer confirmed: true itself on its next call, with nobody asked; the page's button is no gate there either, since an agent calls the operation without it. So nothing that must have a person's yes may rely on either. For a human gate on an agent route, enable ToolGuard in django-spec-agents, whose approval card a person answers before the tool runs, and keep the spec's tool out of its exempt list.
